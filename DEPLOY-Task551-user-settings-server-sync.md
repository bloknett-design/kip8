# DEPLOY — Task 551: Серверная синхронизация настроек пользователя

**Заявка:** «На андроид приложение хранит всю информацию в браузере chrome?
если очистить данные браузера, то приложение "обнуляется". Как обойти
этот момент?»

## Что менялось

### Клиент (index.html) — разойдётся само через SW kipia-v559

- **НОВЫЙ модуль `KipSettingsSync`** — серверная синхронизация настроек
  пользователя (после KipAuth, перед админ-панелью):
  - `restore()` — вызывается во **всех 5 путях входа**
    (`KipAuth._syncUserSettings`): подтягивает настройки с сервера
    (`userSettings.get`) и записывает в localStorage **только
    отсутствующие** ключи (локальные всегда свежее — сервер не
    перетирает); живое применение темы/вида табеля, сброс ленивых
    кэшей избранного (KipFav/KipFavNotes/FlowFav/TempFav/WsLcdClock),
    тост «Настройки восстановлены с сервера (N)»;
  - `save()` — debounce 3 с (`scheduleSave`) при изменении настроек;
    **6 явных хуков** у писателей (тема, вид табеля, перекрёстная
    подсветка, LCD-информер, метод калибровки буёв, реестр
    авто-«д»/«н» Task 458) + **watchdog 60 с** (снапшот localStorage —
    страховка писателей без хука: избранное, закреплённые подразделы,
    ширина панели деталей);
  - белый список из 14 ключей + префикс `kip8_whats_new_read_v*`;
    **НЕ синхронизируются**: токен сессии, кэш роли, кэши серверных
    данных, телефонный справочник (PhonebookArchive Task 537 уже
    синхронит), счёт «Сапёра» (MinesweeperArchive Task 546 уже хранит).
- SW kipia-v558 → **kipia-v559** (двухшаговая схема Task 529:
  гварды v559 → v560 первыми, потом ассерты v558 → v559;
  scripts/task551-bump-sw-kip8.py, 931 замена / 221 файл).

### Сервер (Apps Script) — ТРЕБУЕТСЯ ДЕПЛОЙ

1. Открыть Apps Script Editor проекта **AKfycbyt…** (где Code.gs).
2. `+` → Создать файл **`UserSettingsArchive.gs`** — вставить содержимое
   из `scripts/UserSettingsArchive.gs` репозитория kip8.
3. В **Code.gs** добавить в `doPost` два case (перед `default:`):

   ```js
   case 'userSettings.get':
     return _json(UserSettingsArchive.getMySettings(payload));

   case 'userSettings.save':
     return _json(UserSettingsArchive.saveMySettings(payload));
   ```

   (Эталон Code.gs в репозитории уже обновлён — можно скопировать
   секцию целиком.)
4. В списке функций выбрать **`userSettingsInit`** → ▶ Run
   (первый запуск попросит авторизацию — разрешить). В журнале
   (Ctrl+Enter) — URL таблицы; лист **«Настройки»** появится в
   KIP8_Access среди users/sessions/«Сапёр». Повторные запуски
   идемпотентны.
5. **Deploy → Manage deployments → Edit → New version → Deploy**.
6. Диагностика (по желанию): `userSettingsStatus()` в редакторе —
   таблица/лист/строки/шапка.

Хранилище: лист «Настройки» в KIP8_Access (тот же ID, что
RoleMatrix/MinesweeperArchive), **одна строка на пользователя**
(email из сессии — подделать нельзя), колонки:
`email | имя | данные (JSON) | обновлено`. Гейт — сама сессия
(`Sessions.getCurrentUser`), матрица прав не нужна. Валидация: ключи
только из белого списка (неизвестные молча отбрасываются), значения —
строки ≤ 16 КБ, сумма ≤ 128 КБ. Аудит `USER_SETTINGS_SAVE` — только
число ключей, БЕЗ содержимого (приватность).

## Поведение после деплоя

- **Очистка данных браузера** (Chrome Android/iOS/десктоп, включая
  «Файлы cookie и данные сайтов» установленного PWA): все данные
  разделов остаются в Google Sheets; после повторного входа по OTP
  настройки (тема, вид табеля, избранное приборов/расходомеров/ТС-ТП,
  заметки, закреплённые подразделы, настройки LCD-информера и пр.)
  **восстанавливаются автоматически** + тост. Единственное неизбежное —
  сам повторный вход (токен в браузере не переживает очистку).
- **Новое устройство**: тот же эффект — вход по OTP подтянет настройки.
- **Старый сервер** (без `userSettings.*`): «Unknown action» → тихая
  деградация на локальные настройки, без потери данных; после деплоя
  сервера всё заработает без обновления клиента.
- Данные о праздниках/погоде/телефонах — кэши, перекачиваются сами.
