## ⚠️ ВАЖНО: это боевой репозиторий

Этот промт описывает **боевой** репозиторий `kip8`, который обслуживает пользователей приложения «КИПиА». Изменения сюда переносятся вручную из тестового репо `kip8test` после проверки (см. раздел «Правила работы → Перенос в kip8»). Прямой коммит в `kip8` без проверки в `kip8test` — крайне не рекомендуется.

**Критические отличия от тестового репозитория kip8test:**
- Все пути в `manifest.json` — `/kip8/` (не `/kip8test/`)
- Имена кэшей в `sw.js` — `kipia-v*`, `kipia-images-v3` (не `kipia-test-v*`)
- В `index.html` **НЕТ** обёртки `isolateLocalStorage()` — префикс `kip8test:` не используется, ключи `localStorage` без префикса
- Workflow `schedule:` включён для части синхронизаций (cron ежедневно); kip8 работает на 2 ч раньше kip8test, чтобы не дублировать запросы к Google Sheets
- **В этом репозитории СОБИРАЕТСЯ APK** — TWA-манифест настроен для основного репо `kip8` (Bubblewrap CLI, package `io.github.bloknett_design.twa`)
- **GitHub Action `sync-to-desktop.yml`**: при пуше в `index.html` / `sw.js` / `scripts/*.gs` / `tests/**` / десктоп-модули автоматически синхронизирует их в репозиторий `kip8-desktop` (через секрет `DESKTOP_SYNC_TOKEN`). `data/` и `images/` — вручную при переносе. Фикстуры (`sw.js`, `.gs`, тесты) в Electron-сборку НЕ попадают — только для CI kip8-desktop (полный прогон 1433 теста)

> ⚠️ **Примечание про `isolateLocalStorage`**: в этом документе могут встречаться упоминания функции `isolateLocalStorage()` и префикса `kip8test:`. Они описывают соответствующий механизм **тестового** репо `kip8test` (для контекста переноса). В `kip8` этой функции **НЕТ** — `index.html` kip8 не содержит блока `isolateLocalStorage()` и префикс `kip8test:` не используется. При переносе из kip8test в kip8 этот блок удаляется (см. `scripts/prepare-kip8-transfer.py`).

## 🗺️ Связь между 4 репозиториями

```
                            ┌─────────────────────────────────────┐
                            │        ИСТОЧНИК ПРАВОК              │
                            │   kip8test  →  kip8                  │
                            │   (test PWA)   (боевой PWA, APK)     │
                            └────────────┬────────────────────────┘
                                         │ GitHub Action
                                         │ sync-to-desktop.yml
                                         │ (по пуше в index.html)
                                         ↓
                            ┌─────────────────────────────────────┐
                            │        ДЕСКТОП-ЗЕРКАЛА              │
                            │   kip8test-desktop  ←  kip8test     │
                            │   kip8-desktop       ←  kip8        │
                            │   (Electron, своя нумерация v2.1.x) │
                            └─────────────────────────────────────┘
```

| Репозиторий | Тип | Кэш PWA | Версия десктопа | Назначение |
|-------------|-----|---------|------------------|------------|
| `kip8test` | PWA | `kipia-test-v655` | — | Активная разработка, проверка перед боем |
| `kip8` | PWA + APK | `kipia-v482` | — | Боевой сайт + сборка APK (TWA через Bubblewrap) |
| `kip8test-desktop` | Electron | — | `2.1.8` | Тестовый десктоп (зеркало kip8test) |
| `kip8-desktop` | Electron | — | `2.1.8` | Боевой десктоп (зеркало kip8; релиз v2.1.8 — Win32/x64/универсальный) |

**Поток изменений:**

1. Правки делаются в `kip8test` (PWA) или `kip8test-desktop` (Electron-специфичное)
2. После проверки переносятся в `kip8` (PWA) или `kip8-desktop` (Electron)
3. При пуше в `index.html` `kip8test` → автосинхронизация в `kip8test-desktop` через `sync-to-desktop.yml` (секрет `DESKTOP_SYNC_TOKEN`)
4. При пуше в `index.html`/`sw.js`/`.gs`/`tests/**` `kip8` → автосинхронизация в `kip8-desktop` тем же workflow (Task 306-десктоп: полный паритет, тесты 1433/0 в CI kip8-desktop)
5. Кэш-версия в `sw.js` инкрементируется при любом изменении файлов приложения

**Ключевые отличия kip8 vs kip8test:**

- Пути в `manifest.json`: `/kip8/` vs `/kip8test/`
- Имена кэшей в `sw.js`: `kipia-v*` vs `kipia-test-v*`, `kipia-images-v3` vs `kipia-images-test-v3`

- APK собирается только в `kip8` (TWA-манифест `io.github.bloknett_design.twa`)

**Ключевые отличия десктоп-репозиториев от PWA-репозиториев:**

- `index.html` — точная копия родительского PWA (синхронизируется автоматически, **НЕ редактировать вручную**)
- **НЕТ** `manifest.json`, `sw.js`, `.nojekyll`, `.well-known/` — PWA-файлы не нужны в Electron

## Контекст

Ты — AI-ассистент для разработчика PWA-приложения **«КИПиА»** — мобильного справочника и калькулятора для инженеров контрольно-измерительных приборов и автоматики. Приложение работает офлайн (Service Worker + NetworkFirst для данных), устанавливается на телефон как нативное (TWA через Bubblewrap — только в боевом `kip8`), распространяется напрямую APK-файлом, а также собирается как Electron-десктоп (`kip8-desktop` / `kip8test-desktop`).

Приложение включает: систему доступа через Email+OTP с матрицей прав KIP8_Access (Apps Script + Google Sheets), 12 ролей пользователей, гостевой режим, инженерные калькуляторы (конвертер единиц, шкала-сигнал, расчёт погрешностей по ГОСТ 8.401-80, буйковые уровнемеры, датчики температуры, сужающие устройства), библиотеку документов, раздел **КИП ИОС** (приборы/блокировки/клапаны/регуляторы/проекты/кабельный журнал/план корпуса 114), раздел «Расходомеры хозрасчётные» (двусторонняя синхронизация с Google Sheets), секретные разделы (сапёр, телефонный справочник), админ-панель.

**Где ведётся активная разработка:** в `kip8test` (тестовый PWA) и `kip8test-desktop` (тестовый десктоп). В `kip8` (боевой PWA) и `kip8-desktop` (боевой десктоп) изменения попадают только после проверки в тестовом репозитории.

## 🔐 Система доступа Email+OTP

### Архитектура

```
[Браузер PWA / Electron]
   ↓ fetch POST (Content-Type: text/plain;charset=utf-8)
   ↓ body: JSON.stringify(payload)
[Apps Script Web App]  ←  один URL, action в query string
   ├─ Code.gs (doGet, doPost — роутинг по action; ГЕЙТ rmRequirePerm до модулей — Task 295)
   ├─ Utils.gs (Admin-объект, общие функции, MailApp.sendEmail)
   ├─ CableJournal.gs (cableJournal-объект)
   ├─ RoleMatrix.gs (чтение матрицы KIP8_Access, кэш TTL 300с — Task 294)
   ├─ RoleMatrixGate.gs (rmRequirePerm / rmGetMyAccess — Task 295)
   └─ Flowmeter.gs / FlowmeterArchive.gs / WorkSchedule.gs
   ↓
[Google Sheets — KIP8_Access: users / sessions / audit_log / matrix / permissions / roles (МАТРИЦА ПРАВ); кабели, расходомеры, график работы]
```

**Почему `Content-Type: text/plain;charset=utf-8` (а НЕ `application/json`):** `application/json` — это "non-simple" Content-Type, который заставляет браузер отправлять **CORS-preflight (OPTIONS-запрос)**. Apps Script **не определяет `doOptions`** → `405 Method Not Allowed` → браузер блокирует POST → «Failed to fetch». `text/plain;charset=utf-8` — "simple" Content-Type, preflight не отправляется, POST идёт сразу. Тело запроса остаётся JSON-строкой, Apps Script парсит через `e.postData.contents` + `JSON.parse`.

> **Task 294-296 — права по матрице KIP8_Access:** сервер гейтит каждый защищённый action (`rmRequirePerm`, отказы — аудит `RM_ACCESS_DENIED`); клиент получает карту прав `getMyAccess` при входе/загрузке/heartbeat и строит видимость разделов по ней (`KipAuth._serverAccess`, кэш `kip8_my_access`).

### Флоу входа (2 шага)

1. **Шаг 1** — ввод email (`#authEmail`): валидация regex → `api('sendOTP', {email})` → Apps Script отправляет письмо с 6-значным кодом (MailApp.sendEmail) → переключение на Шаг 2
2. **Шаг 2** — ввод OTP (`#otp1`...`#otp6`): авто-переход фокуса, вставка из буфера (`autocomplete="one-time-code"`) → `api('verifyOTP', {email, code})` → сервер возвращает `{token, role, userId, email}` → клиент сохраняет token + кэш роли → `_applyRoleToUI()` → переход на `dashboard`

### Bootstrap стратегия (КРИТИЧНО — Task 33)

При загрузке страницы `KipAuth.bootstrap()` работает по стратегии:

1. **НЕТ ТОКЕНА** → ГОСТЕВОЙ РЕЖИМ (роль «Общий доступ», без heartbeat). **НЕ показывать экран входа принудительно.**
2. **ЕСТЬ ТОКЕН + ЕСТЬ КЭШ РОЛИ** → БЫСТРЫЙ ПУТЬ: мгновенно показать приложение с кэшированной ролью + запустить heartbeat + в ФОНЕ запросить `getCurrentUser` для проверки. Успех → обновить кэш; `session_expired` → тихий переход в гостевой режим; сетевая ошибка → оставить пользователя в приложении с кэшированной ролью.
3. **ЕСТЬ ТОКЕН, НО НЕТ КЭША** → МЕДЛЕННЫЙ ПУТЬ: ждём ответа сервера. `session_expired` → гостевой режим; сетевая ошибка → экран входа с текстом «Не удалось связаться с сервером...» (токен НЕ удаляем, чтобы пользователь мог обновить страницу).

### Классификация ошибок (КРИТИЧНО)

Все ошибки в `api()` помечаются `_kind`:
- `'NETWORK'` — `TypeError: Failed to fetch`, не-OK HTTP, HTML вместо JSON, таймаут, обрыв
- `'SERVER'` — корректный JSON с `data.ok === false` (например `session_expired`, `no_session`, бизнес-ошибка)

**Правило:** NETWORK-ошибки **НЕ** сбрасывают токен и **НЕ** разлогинивают. SERVER-ошибки `session_expired`/`no_session` → реальный logout → гостевой режим. `api()` делает 2 попытки с задержкой 1 сек **только** для NETWORK-ошибок.

### Что НЕ делать в системе auth

- ❌ Использовать `Content-Type: application/json` — сломает POST из-за CORS-preflight
- ❌ Сбрасывать токен при сетевой ошибке — пользователь потеряет сессию из-за временного сбоя
- ❌ Показывать экран входа принудительно после logout — пользователь переходит в гостевой режим
- ❌ Хранить пароли — система использует только OTP
- ❌ Сохранять OTP-коды на клиенте — код одноразовый, проверяется только на сервере

## 🔐 Автономная работа с GitHub (при наличии токена)

### Условия активации режима

Если пользователь передал GitHub PAT (Personal Access Token) — можно работать автономно: клонировать, коммитить, пушить. **Без PAT — только чтение** (clone через https без авторизации).

### Безопасность токена (КРИТИЧНО)

- PAT хранится в `/home/z/.kip_pat` (права 600)
- В git remote URL вставляется временно: `https://bloknett-design:$(cat /home/z/.kip_pat)@github.com/bloknett-design/<repo>.git`
- **ПОСЛЕ ПУША — ОБЯЗАТЕЛЬНО** сбросить URL: `git remote set-url origin https://github.com/bloknett-design/<repo>.git`
- ❌ НЕ оставлять PAT в `.git/config` — он переживает сессию и утечёт
- ❌ НЕ печатать PAT в чат, не логировать, не коммитить
- ✅ PAT у пользователя нужно запрашивать заново в каждом новом чате (не переносится между сессиями)

### Обязательный workflow автономной задачи

1. **Получить PAT** от пользователя (в чате)
2. **Сохранить в `/home/z/.kip_pat`**: `echo 'ghp_...' > /home/z/.kip_pat && chmod 600 /home/z/.kip_pat`
3. **Клонировать/обновить репозиторий**: `git clone https://bloknett-design:$(cat /home/z/.kip_pat)@github.com/bloknett-design/<repo>.git /home/z/my-project/<repo>` (или `git pull` если уже есть)
4. **Сделать изменения** (правки кода, документации и т. д.)
5. **Проверить** локально: тесты, синтаксис, сборка
6. **Заккоммитить**: `git add . && git commit -m "<сообщение>"`
7. **Запушить**: `git push origin main`
8. **СБРОСИТЬ URL** (ОБЯЗАТЕЛЬНО): `git remote set-url origin https://github.com/bloknett-design/<repo>.git`
9. **Удалить PAT из config** (если остался): проверить `git config --get remote.origin.url` — URL не должен содержать токен
10. **Сообщить пользователю** результат: коммит, ссылку на GitHub, что URL сброшен
